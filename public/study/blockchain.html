1 · What a blockchain is

1.1Definition & core properties★ high yield

BlockchainA decentralised, distributed, immutable digital ledger of records (blocks) securely linked by cryptographic hashes, replicated across a peer-to-peer network and updated only by consensus.
PropertyMeaningWhat provides it

Extra marksHistory for a mark or two: David Chaum (1982) proposed the earliest blockchain-like protocol in his dissertation; Haber & Stornetta (1991) built cryptographically chained document timestamps; Satoshi Nakamoto (2008) added proof-of-work to solve double-spending without a trusted third party; Vitalik Buterin (2013–15) generalised it to arbitrary computation with Ethereum.

1.2Anatomy of a block★ high yieldpast paper

A block = a header + a transaction counter + the body of transactions. Bitcoin's header is exactly 80 bytes.

Header fieldSizePurpose
Version4 BWhich validation rules apply
Previous block hash32 BThe link to the parent — the chain itself
Merkle root32 BOne hash summarising every transaction in the body
Timestamp4 BApproximate creation time (seconds since epoch)
Difficulty target (nBits)4 BHow hard the PoW puzzle is right now
Nonce4 BThe number miners vary to find a valid hash

The genesis block is block 0 — hardcoded, no parent. Every chain begins there.

Extra marksA Merkle tree lets a light client prove one transaction is in a block by supplying only log₂n hashes, not the whole body. For 1,024 transactions that is 10 hashes instead of 1,024. Say this whenever "Merkle root" appears — it is the reason the field exists.

1.3Transaction lifecycle

  1. User creates a transaction and signs it with their private key.
  2. It is broadcast to peers over the gossip protocol.
  3. Nodes validate it (signature valid, funds sufficient, not a double spend) and place it in the mempool.
  4. A miner/validator selects transactions, builds a candidate block and runs the consensus procedure.
  5. The winning block is propagated; other nodes re-verify and append it.
  6. Successive blocks bury it until it is considered final (Bitcoin convention: 6 confirmations).
Exam trap"Confirmed" ≠ "final" on a PoW chain. Finality there is probabilistic — the chance of reversal shrinks with depth but never reaches zero. PBFT-style and PoS-with-checkpointing chains give absolute/economic finality. Examiners love this distinction.

3 · Byzantine fault tolerance & consensus

3.1The Byzantine Generals Problempast paper★ high yield

Byzantine Generals ProblemLamport, Shostak & Pease (1982). Several divisions of the Byzantine army, each led by a general, surround a city. They can communicate only by messenger and must agree on a single plan — attack or retreat. Some generals are traitors who may send contradictory messages. The problem: find a protocol by which all loyal generals agree on the same plan, despite the traitors.

Formally it is the problem of reaching consensus in a distributed system where components may fail arbitrarily — not just by crashing, but by lying, by sending different answers to different peers, or by colluding.

Fault modelWhat a faulty node doesTolerance
Crash / fail-stopStops respondingn ≥ 2f + 1
ByzantineAnything at all, including malicious lyingn ≥ 3f + 1

The classic result: with oral (unsigned) messages, consensus is possible only if more than two-thirds of the generals are loyal — i.e. n > 3f. With signed messages that cannot be forged, any number of traitors can be tolerated.

Extra marksTie it to blockchain in one line: Bitcoin's proof of work is a probabilistic solution to the Byzantine Generals Problem in an open network with unknown membership — it replaces "count the generals" with "count the computation", so an attacker needs 51% of the hash power rather than a third of the identities.

3.2Practical Byzantine Fault Tolerance (PBFT)past paper★ high yield

PBFTCastro & Liskov (1999). The first Byzantine-fault-tolerant algorithm efficient enough for real systems: it tolerates f faulty nodes out of n = 3f + 1, achieves finality in a few communication rounds, and assumes a known, fixed set of participants (hence: permissioned chains).

One node is the primary (leader) for the current view; the rest are backups. Three phases:

  1. Pre-prepare — the primary assigns a sequence number to the client's request and multicasts it.
  2. Prepare — each backup multicasts its agreement; a node is prepared once it has 2f matching prepares.
  3. Commit — nodes multicast commit; on 2f + 1 commits the request is executed and a reply sent to the client.

The client accepts the result once it has f + 1 identical replies. If the primary is faulty or silent, backups trigger a view change and elect the next primary.

PBFTPoW
MembershipKnown, permissionedOpen, anonymous
FinalityImmediate, absoluteProbabilistic
EnergyNegligibleVery high
Message complexityO(n²) — limits it to tens/low hundreds of nodesO(n) gossip
Used byHyperledger Fabric (older), Tendermint/BigchainDB, ZilliqaBitcoin, Ethereum pre-Merge, Litecoin
Exam trapPBFT's O(n²) messaging is why it cannot run a public chain, and that is the single sentence most answers omit. Also: PBFT tolerates f < n/3, not f < n/2.

5 · Ethereum as a platform

5.1Ethereum in the platform comparison★ high yield

EthereumAn open-source, globally decentralised computing infrastructure that executes programs called smart contracts, uses a blockchain to synchronise and store the system's state changes, and uses a cryptocurrency, ether, to meter and constrain execution costs. Formally: a deterministic but practically unbounded state machine with a globally accessible singleton state and a virtual machine (the EVM) that applies changes to it.

As a platform (Module 1's angle — Module 2 goes into the internals):

  • Launched 30 July 2015 (Frontier). Proposed by Vitalik Buterin, 2013; Yellow Paper by Gavin Wood.
  • Generality — Turing-complete contracts in Solidity/Vyper, vs Bitcoin's deliberately limited Script.
  • Largest developer ecosystem and tooling: Remix, Hardhat, Foundry, OpenZeppelin, ERC standards.
  • Standards — ERC-20 (fungible tokens), ERC-721 (NFTs), ERC-1155, ERC-4337 (account abstraction).
  • Weaknesses for enterprise — everything is public to everyone, throughput ~15–30 tps on L1, fees volatile, no identity layer.
Extra marksQuote the enterprise objection from the Corda whitepaper: the public Ethereum architecture is "exceedingly difficult to adapt or adopt … for enterprise use-cases" because all data is shared with all parties. That is the exact gap Fabric, Corda and Quorum were built to fill, and it makes your platform comparison read as an argument rather than a list.

6.3Fabric transaction flow — execute-order-validatepast paper★ high yield

Fabric's signature design. Every other chain is order-execute: order the transactions, then every node runs them. Fabric inverts it.

  1. Propose — the client SDK sends a transaction proposal to the endorsing peers required by the endorsement policy (e.g. "AND(Org1, Org2)").
  2. Execute / endorse — each simulates the chaincode against its world state, producing a read-write set, and signs it. Nothing is written yet.
  3. Collect — the client checks the responses match and assembles them into a transaction.
  4. Order — the ordering service sequences transactions and cuts a block. It never sees the contract logic.
  5. Validate — every committing peer checks the endorsement policy was satisfied and runs MVCC version checks: if a key's version changed since simulation, the transaction is marked invalid.
  6. Commit — the block is appended; valid transactions update the world state; invalid ones stay in the block, flagged.
Extra marksTwo facts examiners reward: (a) invalid transactions are still recorded in the block, just marked invalid — the ledger is a complete audit trail; (b) execute-order-validate removes non-determinism as a consensus problem, which is exactly what allows chaincode in Go/Java rather than a restricted DSL.

6.4Membership and identity managementpast paper

A named past-paper question. Fabric's identity stack:

  • Identity = an X.509 certificate issued by a Certificate Authority. Every actor — peer, orderer, admin, client application — has one.
  • Fabric CA issues, renews and revokes those certificates; any standard CA can be used instead.
  • MSP turns a certificate into a role in an organisation: it holds the org's root CAs, intermediate CAs, admin certs, and the revocation list. "Which certificates count as Org1?" is answered by Org1's MSP.
  • Local MSP (on a node, defines who administers it) vs Channel MSP (defines org membership and rights on a channel).
  • Principal / policy — access control is written against MSP roles: Org1MSP.peer, Org1MSP.admin, Org1MSP.member.
  • Idemix — optional zero-knowledge credentials giving unlinkable, anonymous-but-authorised transactions.
Extra marksOne line that lands the concept: PKI provides the identity, the MSP provides the meaning. PKI says "this certificate is genuine"; the MSP says "and a genuine certificate from this CA counts as an administrator of Org1".

8 · MultiChain

8.1MultiChain★ high yield

MultiChainA distributed database for multi-asset financial transactions which uses an enhanced version of Bitcoin's blockchain technology inside a private peer-to-peer network. Built by Coin Sciences Ltd (Dr Gideon Greenspan). Because it is a Bitcoin fork, it keeps the UTXO model and offers a rich JSON-RPC API that is a superset of Bitcoin Core's.

Straight from the MultiChain 1-pager in your folder — the five enhancements over a standard blockchain:

EnhancementWhat it means
Native multi-currencyAny number of assets issued and transacted in one network; quantities verified at network level, enabling atomic two- or multi-way exchange
Permission managementAdministrators control exactly who may connect, create assets, and send / receive / confirm ("mine") transactions. Permissions are themselves stored and enforced via the blockchain
Rapid deploymentTwo commands to create a network, three to add a node — no manual configuration management
Multi-networkOne server can connect to several chains simultaneously
Per-network custom parametersPermitted transaction types, target confirmation time, minimum quantities, transaction rate and size limits

Target users: banks, financial institutions and service providers experimenting with blockchain — an off-the-shelf but highly configurable platform that accelerates research versus bespoke development. Runs on Windows and Linux servers.

Extra marksMultiChain's distinctive consensus is mining diversity. It keeps proof of work in form but strips the arms race: only permitted miners may create blocks, and a parameter mining-diversity (0–1) forces the round-robin — a miner may not create a block until a given proportion of the other permitted miners have had their turn. This blocks a single permitted miner from monopolising the chain, with no energy burn.
Exam trapMultiChain has no native cryptocurrency and no block reward. "Mining" is only the act of confirming; assets are issued by permitted parties, not mined.

11 · R3 Corda

11.1Corda — what it is and why★ high yield

CordaDistributed-ledger software from R3 (a consortium of 200+ financial institutions) for recording and processing shared data such as contracts. Designed to record and automate legal agreements between identifiable parties, with privacy, identity and legal enforceability at its core. Open source since 2016; written in Kotlin/Java on the JVM.

The motivating problem, in R3's own words: managing agreements between firms "when those parties trust each other enough to trade but not enough to have their counterparty maintain all the records". Today every institution keeps its own ledger, so the industry pays for endless reconciliation. Corda's promise: "I know that what I see is what you see."

11.2Corda's two-part consensus★ high yield

Corda splits consensus into two independent questions — this is the single most examinable thing about it:

  1. Transaction validity — parties independently run the same deterministic contract code, check all required signatures, and recursively check the transactions this one depends on. Performed only by the parties to the transaction.
  2. Transaction uniqueness — is this the unique consumer of all its input states? Answered by a notary, which may be a single machine or a pool of mutually distrusting nodes running a BFT algorithm.

Crucially, the notary is not required to see the transaction contents — it only attests that the input states have not been consumed before. That is what makes validity checking private and the uniqueness service scalable.

Extra marksThere is no global broadcast in Corda. "A transaction between a group of parties is visible only to them, and to those whose own view of the ledger may depend on verifying its validity." Everywhere else — Bitcoin, Ethereum, even Fabric channels — consensus happens at the ledger level. Corda reaches consensus at the level of the individual agreement. Say this and the examiner knows you have read the whitepaper.

13 · IPFS

13.1IPFS — InterPlanetary File Systempast paper★ high yield

IPFSA peer-to-peer content-addressed distributed file system (Juan Benet, Protocol Labs, 2014). Files are addressed by the hash of their content rather than by location, so the same content always has the same address, and any peer holding it can serve it. IPFS is not a blockchain — it stores no ledger and has no consensus.
MechanismWhat it does
Content addressing / CIDAddress = a multihash of the content. Identical files deduplicate automatically; a changed byte changes the address
Merkle DAGFiles are chunked (default 256 KB) and linked into a Merkle directed acyclic graph — this gives verification, deduplication and partial fetching
DHT (Kademlia)A distributed hash table that answers "which peers have this CID?"
BitswapThe block exchange protocol — the want-list / have-list trading between peers
libp2pThe networking stack: transport, discovery, NAT traversal, multiplexing
IPNSMutable naming — a key-signed pointer to a changing CID, since CIDs themselves are immutable
PinningMarking content so a node does not garbage-collect it. Nothing persists unless someone pins it (Pinata, Infura, or your own node)

Why every blockchain course teaches it: on-chain storage is brutally expensive — storing a kilobyte on Ethereum costs orders of magnitude more than a database. The standard pattern is therefore store the file on IPFS, store only the CID on-chain. The hash on-chain proves integrity; the bytes live off-chain. Every NFT you have heard of works this way.

Extra marksTwo additions that pay: (a) Filecoin is the incentive layer built on IPFS — IPFS gives you addressing and transport but no guarantee anyone stores your file, and Filecoin adds a market with cryptographic proofs of storage (proof-of-replication, proof-of-spacetime). (b) IPFS achieves the "permanent web": HTTP breaks when a server moves a file, but a CID resolves to the content wherever it lives.
Exam trapIPFS does not guarantee permanence. Content that nobody pins is garbage-collected and disappears. "IPFS stores files forever" is false and is a favourite trap.

14 · DApps

14.1Decentralised applicationspast paper★ high yield

DAppAn application whose backend logic runs on a decentralised peer-to-peer network rather than a central server. The four criteria usually quoted (Johnston et al., The General Theory of Decentralized Applications): it is open source and operates autonomously with no entity controlling a majority of its tokens; its data and records are cryptographically stored on a public, decentralised blockchain; it uses a cryptographic token for access and for rewarding contributors; and it generates tokens by a consensus algorithm.

15.1Do you even need a blockchain?★ high yield

The syllabus's last Module 1 line. Answer it in two stages: first should this be a blockchain, then which platform.

19 · Turing completeness & verification challenges

19.1Turing completeness★ high yield

Turing completeA system is Turing complete if it can be used to simulate any Turing machine — such a system is a universal Turing machine (UTM). Ethereum's ability to execute a stored program in a state machine (the EVM) while reading and writing memory makes it Turing complete: it can compute any algorithm computable by a Turing machine, given finite memory.

Alan Turing, 1936: a mathematical model of a computer — a state machine manipulating symbols on an infinite tape. With it he proved that some problems are uncomputable. Specifically, the halting problem — given an arbitrary program and input, decide whether it will eventually stop — is unsolvable.

Ethereum's innovation is combining the general-purpose architecture of a stored-program computer with a decentralised blockchain, creating a distributed single-state (singleton) world computer.

19.2Turing completeness is a danger, not a feature★ high yield

The counter-intuitive point the textbook makes, and the one that separates a strong answer:

  • Turing completeness is trivially easy to achieve — the simplest known Turing-complete state machine has 4 states, 6 symbols and a 22-instruction definition. Systems are sometimes found to be "accidentally Turing complete".
  • It is dangerous in open-access systems precisely because of the halting problem. Modern printers are Turing complete and can be sent a file that freezes them — and an unresponsive printer can be switched off. A public blockchain cannot.
  • Every node must validate every transaction, running any contract it calls. Ethereum cannot predict whether a contract will terminate, or how long it will run, without running it.
  • So a contract can be written — by accident or on purpose — that runs forever when a node validates it. That is a denial-of-service attack on the whole network. Between "one millisecond" and "forever" lies an infinite range of resource-hogging, memory-bloating programs.
  • "In a world computer, a program that abuses resources gets to abuse the world's resources."
Gas — the answerA metering mechanism. As the EVM executes, it accounts for every instruction; each has a predetermined cost in gas. A transaction must include a gas limit setting the upper bound of what may be consumed. If execution exceeds the gas available, the EVM terminates it. Gas is how Ethereum permits Turing-complete computation while bounding the resources any program can consume.
Extra marksGas does not solve the halting problem — that is mathematically unsolvable. It sidesteps it: rather than deciding in advance whether a program halts, Ethereum makes non-halting expensive and self-limiting. Every node knows execution stops when the gas runs out, without ever deciding whether it would have stopped on its own. State that distinction and the answer is complete.
Exam trapWhen a transaction runs out of gas, the state changes are reverted but the gas is still consumed and paid. The user pays for a failed transaction. That asymmetry is what makes the DoS attack uneconomic — and it is a favourite one-mark question.

Ethereum clientA software implementation of the Ethereum specification that verifies transactions and blocks against the consensus rules and communicates with other nodes over the P2P network. A node is a running instance of client software.

23.2Private key → public key → address★ high yield

  1. Private key — a random 256-bit number k, valid if 0 < k < n (n = the order of the secp256k1 curve). 32 bytes, 64 hex characters.
  2. Public key — K = k · G, elliptic-curve point multiplication on secp256k1. G is the generator point. This is one-way: deriving k from K is the discrete-logarithm problem.
  3. Address — take the 64-byte uncompressed public key (drop the 04 prefix), hash with Keccak-256, keep the last 20 bytes, prefix with 0x.

EIP-55 checksum: Ethereum addresses have no built-in checksum, so EIP-55 encodes one in the capitalisation of the hex letters — a wallet can detect a mistyped address without changing the address format.

Exam trapEthereum uses Keccak-256, not the finalised NIST SHA-3. Ethereum adopted Keccak before standardisation and the padding differs, so the two produce different digests. Also: the transaction has no "from" field — the sender's public key, and hence the address, is recovered from the ECDSA signature (v, r, s). Explorers add the "from" column for display.

24.2Deployment, the ABI, and the token standards

Deployment: compile → bytecode + ABI. Send a transaction with no recipient (to empty) and the init bytecode as data. The EVM runs the init code, stores what it returns as the contract's runtime code, and assigns the address keccak256(rlp(sender, nonce))[12:].

26 · Miners

26.1Mining as the syllabus means itnamed in syllabus

MinerUnder Proof of Work, a node that collects transactions from the mempool, assembles a candidate block, and repeatedly hashes the header with varying nonces until the digest falls below the difficulty target. The first to succeed broadcasts the block and receives the block reward plus transaction fees.
AspectEthereum PoW (2015 – Sept 2022)
AlgorithmEthash — memory-hard, built on a ~1 GB DAG regenerated each epoch (30,000 blocks), deliberately ASIC-resistant to keep mining on consumer GPUs
Block time~13–15 seconds, held there by difficulty adjustment every block
Block reward5 ETH → 3 (Byzantium) → 2 ETH (Constantinople), plus fees
Ommer/uncle rewardA stale-but-valid block could be included by a later block; its miner received up to 7/8 of the reward and the includer a bonus. Short block times cause many orphans — this stops small miners being wiped out
Fork choiceGHOST — Greedy Heaviest Observed Subtree: count the whole subtree's work, not just the longest chain, so orphaned work still contributes to security
Mining poolMiners combine hash power and share rewards in proportion to submitted shares, smoothing income
Attack51% — a majority of hash power allows double-spends and censorship, but not stealing coins or forging signatures

26.2What actually happens now — Proof of Stake★ high yield

Exam trap — the single most likely trap in this paperEthereum has had no miners since 15 September 2022. The Merge replaced PoW with Proof of Stake. If a question says "explain the role of miners in Ethereum", the full-marks answer describes PoW mining as the syllabus expects and then adds one sentence saying it was replaced by validators at The Merge. Writing only the old story is incomplete; writing only the new story does not answer the question asked.

27 · Transaction and Block in Ethereum

27.1Transaction structurepast paper★ high yield

TransactionA signed message originated by an externally owned account, serialised with RLP and recorded on the blockchain. Transactions are the only thing that can trigger a state change or cause a contract to execute.

Legacy transaction fields:

FieldMeaning
chain IDWhich network (EIP-155) — replay protection across chains
nonceSequence number from the originating EOA; prevents replay and fixes ordering
gas priceWei the sender will pay per unit of gas
gas limitMaximum gas to buy. You pay only for gas actually used
recipient (to)Destination address — empty for a contract deployment
valueWei to transfer
dataVariable-length payload — the ABI-encoded function call, or the init bytecode
v, r, sThe three components of the ECDSA signature

Typed transactions (EIP-2718) put a type byte in front:

TypeNameAdds
—LegacyThe original format
0x01EIP-2930Access list — prepay for addresses/storage slots to get cheaper "warm" access (SLOAD is 100 gas warm, 2,100 cold)
0x02EIP-1559 (London, Aug 2021)Replaces gas price with max priority fee per gas (the tip) and max fee per gas (the total ceiling)
0x03EIP-4844 (Cancun, Mar 2024)Blob-carrying transactions for rollup data
Extra marksExplain EIP-1559 properly: the base fee is set by the protocol from block fullness — it rises when a block exceeds the 15M gas target and falls when it is under — and it is burned, not paid to anyone. Only the priority fee reaches the validator. So under heavy use Ethereum destroys more ETH than it issues, which is why the network is described as deflationary. Block gas limit went from 15M to 30M with a 15M target in the same upgrade.
Exam trapA simple EOA→EOA transfer costs exactly 21,000 gas. That number is worth memorising — it appears in numerical questions ("compute the fee at 3 gwei": 21,000 × 3 gwei = 63,000 gwei = 0.000063 ETH).

27.2Block structurepast paper★ high yield

An Ethereum block = header + transaction list + (historically) ommer list. The header commits to three tries:

Header fieldMeaning
parentHashHash of the previous block header — the chain link
ommersHashHash of the uncle list (constant since the Merge)
beneficiary / feeRecipientAddress that receives fees — the miner, now the validator
stateRootRoot of the state Merkle Patricia trie after this block
transactionsRootRoot of the trie of transactions in this block
receiptsRootRoot of the trie of transaction receipts
logsBloomA 2048-bit Bloom filter over the logs — lets a client skip blocks that cannot contain an event
difficulty / prevRandaoPoW difficulty; repurposed after the Merge to carry the PoS randomness beacon
numberBlock height
gasLimit / gasUsedCeiling for the block, and what was consumed
timestampUnix time of the block
extraDataUp to 32 arbitrary bytes
mixHash / noncePoW proof (zeroed post-Merge)
baseFeePerGasAdded by EIP-1559 — the burned portion of the fee
Extra marksThree roots, three tries: state, transactions, receipts. The state trie is a Merkle Patricia Trie, which combines a Merkle tree (tamper evidence) with a radix trie (key lookup by path). Because state changes every block, sharing unchanged subtrees between blocks is what makes it feasible at all — and stateRoot is a single 32-byte commitment to the balance of every account in the world.
Exam trapBitcoin's block header has one Merkle root; Ethereum's has three, and Bitcoin has no notion of a state root at all — because Bitcoin's state is the UTXO set, derived by replaying transactions, whereas Ethereum commits to its state explicitly. That contrast is a ready-made comparison answer.

28 · Front end development

28.1The DApp front endnamed in syllabus★ high yield

The last syllabus line for Module 2. A DApp front end is an ordinary web page — HTML, CSS, JavaScript — whose backend calls go to a blockchain instead of a server.

The connection flow — worth writing as numbered steps:

  1. MetaMask injects an EIP-1193 provider at window.ethereum.
  2. The page calls eth_requestAccounts; the user approves the connection.
  3. The page builds a contract handle from the ABI + address.
  4. Reads use .call() → eth_call: instant and free.
  5. Writes use .send() → MetaMask shows a confirmation with the estimated gas → the user signs → eth_sendRawTransaction.
  6. The page shows "pending", waits for the receipt, then updates.
  7. It subscribes to events over WebSocket to reflect changes made by other users.
