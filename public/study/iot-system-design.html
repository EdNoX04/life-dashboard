Module 1 · Embedded IoT

1 · What IoT is

1.1Definitions★ high yield

IoT — the formal definition (Bahga & Madisetti)A dynamic global network infrastructure with self-configuring capabilities based on standard and interoperable communication protocols, where physical and virtual "things" have identities, physical attributes and virtual personalities, use intelligent interfaces, are seamlessly integrated into the information network, and often communicate data associated with users and their environments.
IoT — the working definitionA network of physical objects — devices, vehicles, buildings and other items — embedded with electronics, software, sensors and network connectivity, which enables these objects to collect and exchange data.

Learn both. The formal one wins marks in a "define IoT" question; the working one is what you use in every other answer.

The five characteristics of IoT:

CharacteristicMeaning
Dynamic and self-adaptingDevices adapt their behaviour to changing context — a camera switching to night mode
Self-configuringDevices set themselves up, join networks and update firmware with little user action
Interoperable communication protocolsThey speak standard protocols so different vendors' devices work together
Unique identityEvery device has an identifier (IP, MAC, URI) and a management interface
Integrated into the information networkDevices are not isolated — they describe themselves and communicate their state
Extra marksNote the phrase most students skip: "physical and virtual things". IoT is not only hardware — a virtual thing (a software resource, a digital twin, an avatar of a physical device) counts too. Quoting that clause shows you read the definition rather than paraphrased it.

1.2Why IoT, and what "things" means

Why IoT: dynamic control of industry and daily life · improves the resource-utilisation ratio · integrates human society and physical systems · flexible configuration · acts as a technology integrator · universal inter-networking.

"Things" in IoTWhat it means
Tagging thingsReal-time item traceability and addressability by RFID
Feeling thingsSensors as the primary devices collecting data from the environment
Shrinking thingsMiniaturisation and nanotechnology making devices small enough to embed anywhere
Thinking thingsEmbedded intelligence — devices connected to the internet that realise intelligent control

The three scopes of "things": people, machines and information. IoT is not the result of a single novel technology — several complementary developments together bridge the gap between the virtual and physical world.

The eight capabilities that bridge those worlds: communication and cooperation · addressability · identification · sensing · actuation · embedded information processing · localisation · user interfaces.

Extra marksDistinguish the three that sound alike, because a question will: identification is knowing which thing this is (an RFID tag, a UUID); addressability is being able to reach it and configure it (an IP address); localisation is knowing where it is (GPS, RSSI trilateration). Getting those three apart is a whole mark on its own.

3 · Embedded systems

3.1Definition and characteristics★ high yield

Embedded systemA combination of computer hardware and software — often with mechanical parts — designed to perform a specific, dedicated function or a small set of functions, usually as part of a larger machine or system.

How it differs from a general-purpose computer: runs one dedicated program, not arbitrary user applications · tightly coupled to the physical world through sensors and actuators · resource-constrained in memory, processing and energy · usually invisible to the end user, being embedded inside a product.

#CharacteristicMeaning
1Single-purposeOptimised for one task or a narrow family of related tasks
2Autonomous operationRuns on its own, continuously, without ongoing human intervention
3Real-time constraintsResponses must occur within strict, predictable time bounds
4Reactive & always-onContinuously senses and reacts to the physical world, often 24×7
5Resource-constrainedTight limits on memory, processing, energy and cost
6Tightly coupled to hardwareFirmware written close to, and tuned for, a specific microcontroller

Purposes an embedded system serves (any one or a combination): data collection / storage / representation · data communication · data (signal) processing · monitoring · control · application-specific user interface.

Everyday examples: microwave oven, digital camera, automotive ECU, Wi-Fi router, washing machine, smartwatch, traffic-light controller, printer, industrial robot, GPS receiver, set-top box, ATM, medical device.

3.4Classification, co-design and ICEfrom deck 4

SystemA way of working, organising or doing one or many tasks according to a fixed plan, program or set of rules.

Embedded systems are classified by complexity — small-scale (8-bit MCU, battery powered, e.g. a toy), medium-scale (16/32-bit, RTOS, e.g. a router) and sophisticated/large-scale (ASIC/FPGA, multiple processors, e.g. an avionics controller) — and by timing as real-time (hard vs soft), networked, mobile and stand-alone.

Classic design flowHardware/software co-design
PartitioningSystem partitioned into hardware and software immediatelyPartitioning decided during design, from performance criteria
DevelopmentHardware and software developed separatelyConcurrent — both developed at the same time on parallel paths
InteractionHW/SW trade-offs restricted; impact of each on the other cannot be assessed easilyIntegrated — interaction between the two produces designs meeting performance and functional specifications

In-Circuit Emulator (ICE)A debugging tool that gives access to a target microcontroller for in-depth debugging. Once code is created, edited and compiled on a host computer, the executable object code must be uploaded to the microcontroller — an ICE lets you run and inspect it on the real target hardware, with breakpoints, single-stepping and register inspection, rather than only in a simulator.

Role of embedded systems in IoT: real-time computing · low power consumption · low maintenance · high availability. These four properties are why IoT nodes are embedded systems rather than small PCs.

4.1Microprocessor vs microcontroller★ high yield

The full processor taxonomy a question may ask for: General-Purpose Processor (GPP) — microprocessor, microcontroller, embedded processor, DSP (digital signal processor), media processor; ASSP (application-specific system processor); ASIP (application-specific instruction-set processor); ASIC (fully custom silicon); and FPGA (reconfigurable logic).

Extra marksGive the trade-off axis rather than only the list: moving GPP → DSP → ASIP → ASIC buys performance-per-watt and unit cost at high volume, and pays in flexibility and NRE cost — an ASIC cannot be changed after fabrication, an FPGA sits in between because it is reconfigurable. That sentence is the reason the taxonomy exists.

4.2The Arduino platform★ high yield

ArduinoAn open-source electronics platform combining a microcontroller board with a simple software IDE. Code written on a computer is compiled and uploaded to the physical board, where it runs standalone.
Development boardA printed circuit board designed to make working with a particular microcontroller easy. Typical components: power circuit, programming interface, basic input (buttons and LEDs) and I/O pins.

What it does: designed for artists, designers, hobbyists and engineers building interactive objects. It can read buttons and sensors and drive LEDs, motors, speakers, GPS units and cameras — even talk to the internet or a smartphone.

Why it matters for IoT: low cost, a huge community and a simplified programming model make Arduino — and its IoT-ready cousins like the ESP8266 and ESP32 — the most common entry point for prototyping before production hardware.

The typical workflow, in six steps: write the sketch in C/C++ in the IDE → compile for the target board → upload firmware over USB/serial → the board runs the program standalone → connect sensors and actuators to the GPIO pins → iterate by re-uploading.

5.2Writing the purpose and requirement specification★ high yield

Purpose & requirement specificationThe first step of IoT system design: state the purpose — the problem the system solves and for whom — then the behaviour, the system management requirements, the data analysis requirements, the application deployment requirements and the security requirements.
PartWhat to write

Functional vs non-functional requirements — a distinction the examiner will reward:

FunctionalNon-functional
DescribesWhat the system doesHow well it does it
Examples"Read temperature every 30 s", "turn on the light when motion is detected", "send an alert above 40 °C"Accuracy ±0.5 °C · latency under 2 s · battery life 6 months · 99% uptime · cost under ₹1,500 · works offline for 24 h

Worked example — a smart cold-storage trackerPurpose: monitor temperature and humidity inside a cold-storage unit so that spoilage is prevented and a compliance record exists. Behaviour: samples every 60 s; in auto mode raises an alarm and switches on the backup compressor above 8 °C; in manual mode the operator controls the compressor from the app; if the network is down, readings are buffered locally and uploaded on reconnection. System management: device health and firmware version visible remotely; OTA update supported. Data analysis: threshold checking on-device (must not depend on the network); trend analysis and monthly compliance reports in the cloud. Application deployment: cloud-hosted dashboard plus a mobile app. Security: per-device credentials, TLS in transit, role-based access to the dashboard. Non-functional: ±0.5 °C accuracy, alert within 10 s of breach, 24 h of local buffering, mains-powered with battery backup.

7 · Functional view specification

7.1What the functional view isnamed in syllabus★ high yield

Functional viewThe specification of WHAT the system does. It defines actors, system boundaries and data flows; shows the logical functions — sensing, processing, communicating, storing; identifies the interfaces between subsystems; and is technology-independent, describing behaviour rather than components. It answers: what inputs and outputs? what processing occurs? what data flows where?

8 · Operational view specification

8.1What the operational view isnamed in syllabus★ high yield

It shows the physical deployment of hardware and network elements; identifies the communication protocol per link (Wi-Fi, MQTT, HTTP); maps physical locations — field device, gateway, cloud; and includes network topology and infrastructure constraints. It answers: which hardware? which protocol? how are the nodes connected?

The operational view groups to write about: devices and their operating system · communication — the actual link, network, transport and application protocols chosen · services — native service, REST/WebSocket services · application — web app, mobile app · security — the actual mechanisms · management — the tools used.

Extra marksThe reason the two views are separated is worth one sentence: the functional view survives a change of hardware; the operational view does not. If the DHT11 is replaced with a BME280 and MQTT with HTTP, the functional view is untouched — "sense temperature, publish reading" is still true. That is the whole point of specifying them separately, and stating it shows you understand the method rather than the diagram.

9 · Device & component integration

9.1Integration, and then the applicationnamed in syllabus

Device & component integrationStep 9 of the methodology: the physical and logical wiring-up of the chosen components — connecting sensors and actuators to the device, installing the controller service, connecting the device to the network and to the cloud services, and verifying that data flows end to end.

What integration actually involves:

  1. Electrical — correct supply voltage, common ground, logic-level compatibility (a 5 V sensor output into a 3.3 V ESP pin needs a divider), current budget, pull-up resistors where the bus needs them.
  2. Interface — choosing and wiring the right bus per component: GPIO, analog in, UART, I2C or SPI, and resolving address clashes on I2C.
  3. Driver / library — installing the sensor library and confirming it reads sane values before anything else is built.
  4. Controller service — the on-device program that reads resources and talks to the web service.
  5. Connectivity — joining Wi-Fi, reaching the broker or REST endpoint, handling reconnection.
  6. End-to-end verification — a reading taken at the sensor appearing, correct and timestamped, in the cloud database.

Step 10, application development, then builds the interface on top: dashboards, controls, alerts and reports over the stored data.

Exam trapIntegration is where logic levels kill projects. The Arduino Uno is a 5 V board; the ESP8266 and ESP32 are 3.3 V and their GPIO pins are not 5 V tolerant. Wiring a 5 V sensor output straight to an ESP pin can destroy it. Mention a level shifter or a voltage divider whenever a design mixes the two — it is the kind of practical detail that separates a lab answer from a textbook one.

11 · Logical design & communication models

11.1Logical design

Logical designAn abstract representation of the entities and processes of an IoT system, without going into the low-level specifics of the implementation. An IoT system comprises a number of functional blocks that give it the capabilities for identification, sensing, actuation, communication and management.

11.2The four communication models★ high yield

ModelHow it worksCouplingReal protocol
Request–responseThe client sends requests; the server decides how to respond, fetches the data, retrieves resource representations, prepares and sends the response. Stateless — each request is independentClient must know the serverHTTP / REST, CoAP
Publish–subscribeInvolves publishers, brokers and consumers. Publishers send data to topics managed by the broker and are not aware of the consumers. Consumers subscribe to topics; when the broker receives data for a topic it sends it to all subscribersFully decoupled by the brokerMQTT, AMQP
Push–pullProducers push data into queues; consumers pull from them. Producers need not know the consumers. Queues decouple the two and act as a buffer when production and consumption rates differDecoupled by the queueAMQP queues, Kafka
Exclusive pairBidirectional, full-duplex, using a persistent connection between client and server. Once set up it stays open until the client closes it; either side may send at any time. StatefulTightly coupled, one-to-oneWebSocket
REST-based communication APIsRepresentational State Transfer is a set of architectural principles for designing web services and APIs that focus on a system's resources and how resource states are addressed and transferred. REST APIs follow the request–response model, and its constraints apply to the components, connectors and data elements of a distributed hypermedia system.
WebSocket-based communication APIsAllow bi-directional, full-duplex communication between clients and servers, following the exclusive pair model.
Extra marksREST's constraints are worth naming if the question is worth 5 marks or more: client–server, stateless, cacheable, layered system, uniform interface and optionally code on demand. "Stateless" is the one with IoT consequences — every request carries its own context, which is why REST scales but also why a device must re-send its identity every time, and why MQTT is cheaper for a sensor reporting every ten seconds.

11.3IoT design principlesfrom deck 7

  • Interoperability — devices from different vendors must work together, which is why standard protocols and data formats matter more than any single clever design.
  • Decentralisation — pushing decisions to the edge rather than requiring a round trip to a central server for every action; this is the design principle behind fog computing.
  • Scalability — the design must work for ten devices and ten thousand.
  • Security and privacy by design — retrofitted security fails, because constrained devices have no headroom to add it later.

Wireless network types the deck contrasts: infrastructure-based, where wireless clients connect to a base station (AP) that provides all the traditional network services; and infrastructure-less (ad hoc), where the clients must provide those services to each other. Ad hoc networks are further classified by topology into homogeneous (one platform throughout) and heterogeneous (mixed platforms).

IoT platformThe middleware sitting between IoT gateways/hardware and the application and business layers. How it works: the transmitter emits an ultrasonic wave; the wave reflects off an object and returns to the receiver. The module holds the Echo pin high for exactly the round-trip time. Since the speed of the wave in air at room conditions is known (≈ 330 m/s; 343 m/s at 20 °C is also accepted), the microcontroller computes:

distance_cm = (echo_time_us × 0.0343) / 2;
// or the classic shortcut:

Exam trapDivide by two. The measured time is the round trip; forgetting the halving doubles every distance and is the single most common error in this calculation. 23 · Digital I/O

23.1The three functions★ high yield

Digital I/O is binary — on or off, 1 or 0. Internally all microprocessors are digital, because two well-separated voltage levels are far more noise-tolerant than a continuum.

FunctionDoes
pinMode(pin, mode)Sets the pin to INPUT, OUTPUT or INPUT_PULLUP
digitalRead(pin)Reads HIGH or LOW from a pin
digitalWrite(pin, value)Writes HIGH or LOW to a pin

The electrical facts the deck gives: output pins can provide 40 mA of current; writing HIGH to an input pin installs a 20 kΩ pull-up resistor (this is what INPUT_PULLUP does explicitly).

// Exercise 1: a push button turning an LED on and off
const int BUTTON = 2, LED = 13;

void setup() {
  pinMode(BUTTON, INPUT_PULLUP);   // internal pull-up: no external resistor
  pinMode(LED, OUTPUT);
}
void loop() {
  // With a pull-up the logic is INVERTED: pressed reads LOW
  if (digitalRead(BUTTON) == LOW) digitalWrite(LED, HIGH);
  else                              digitalWrite(LED, LOW);
}
Exam trapA digital input pin must never be left floating — an unconnected input picks up noise and reads randomly HIGH and LOW. Every button needs a pull-up or pull-down resistor, and with a pull-up the pressed state is LOW, not HIGH. Getting that inversion the wrong way round is the standard lab mistake and a standard viva question.

25 · Analog output & PWM

25.1Pulse width modulation★ high yield

Can a digital device produce analog output? Not truly — but it can be simulated using pulse width modulation.

PWMYou cannot use a digital pin to supply, say, 2.5 V directly, but you can pulse the output on and off very fast to produce the same effect. The pulsing happens so quickly that the connected output device "sees" the result as a reduction in voltage. The cycle length is fixed, with a constant number of cycles per second; what varies is the duty cycle.
output voltage = (on_time / cycle_time) × 5 V

analogWrite(pin, value)   // value is the duty cycle, 0 … 255
analogWrite(9, 128)        // 50% duty cycle  -> ~2.5 V average
analogWrite(11, 64)        // 25% duty cycle  -> ~1.25 V average

PWM-capable pins on the Uno: 3, 5, 6, 9, 10, 11 — marked with a tilde (~) on the board. Default PWM frequency is about 490 Hz (980 Hz on pins 5 and 6).

Uses: LED brightness, DC motor speed through a driver, servo position, and generating tones on a passive buzzer.

Exam trapPWM is not a true DAC. The pin is still only ever at 0 V or 5 V; the average is what varies. That matters in practice: an LED or a motor integrates the pulses and behaves as if it saw the average, but a circuit that needs a genuine steady voltage — a reference, an analog input to another device — needs an RC low-pass filter or a real DAC. Say this and the difference between analogWrite and analog output is clearly understood.

  2. Download the firmware — the .bin for ESP8266 from micropython.org/download.
  3. Connect the board by USB and find the port (/dev/ttyUSB0, COM3).

# 4 — erase

>>> led = machine.Pin(2, machine.Pin.OUT)
>>> led.value(0)      # on — the built-in LED is ACTIVE LOW

Exam trap — three things that break ESP sensor wiring(1) The ESP8266 has exactly one analog pin (A0). Two analog sensors need an external ADC (ADS1115 over I2C) or an analog multiplexer — this is a favourite "why won't this design work" question. (2) GPIO pins are 3.3 V and not 5 V tolerant: the HC-SR04's ECHO output is 5 V and must go through a divider (1 kΩ + 2 kΩ) or it can damage the pin. (3) Sensors needing 5 V take it from VIN, not 3V3, and every device must share a common ground — a floating ground is the reason "the sensor reads nonsense".

import network, time

def connect(ssid, password, timeout=15):
    wlan = network.WLAN(network.STA_IF)   # station interface
    wlan.active(True)
    if not wlan.isconnected():
        print('connecting…')
        wlan.connect(ssid, password)
        t0 = time.time()
        while not wlan.isconnected():
            if time.time() - t0 > timeout:   # ALWAYS bound the wait
                raise OSError('wifi timeout')
            time.sleep(0.5)
    print('ifconfig:', wlan.ifconfig())    # (IP, netmask, gateway, DNS)
    return wlan

# Put this in boot.py so the board is online before main.py runs
connect('MyNetwork', 'password')

Useful calls: wlan.scan() lists nearby networks · wlan.status() reports why a connection failed · wlan.ifconfig() returns the IP tuple · network.WLAN(network.AP_IF) with .config(essid=…, password=…) starts an access point.

Extra marksThree practical points worth a mark each. (1) The ESP8266 is 2.4 GHz only — it cannot see a 5 GHz network, which is the most common "it won't connect" cause. (2) Always bound the connection wait; a while not connected: pass loop hangs the board forever if the router is down. (3) Wi-Fi is the dominant power draw, so battery designs connect, publish and immediately deepsleep rather than staying associated.

On a device with ~50 KB of heap, a request loop that leaks sockets runs for a few hundred iterations and then dies with a memory allocation error — a fault that looks random and is not. 32 · MQTT

32.1The protocolnamed in syllabus★ high yield

MQTTMessage Queuing Telemetry Transport — a lightweight publish–subscribe messaging protocol over TCP, designed for constrained devices and unreliable, low-bandwidth networks. Publishers send messages to topics on a broker; subscribers receive every message on the topics they subscribe to. Publishers and subscribers never know about each other.
ConceptMeaning
BrokerThe server that receives all messages and routes them — Mosquitto, HiveMQ, AWS IoT Core
TopicA hierarchical string: home/livingroom/temperature. Wildcards: + one level, # all remaining levels
PublishSend a payload to a topic

QoS 0At most once — fire and forget
QoS 1At least once — acknowledged, may duplicate
QoS 2Exactly once — four-way handshake, most overhead
Retained messageThe broker keeps the last message on a topic and gives it to new subscribers immediately

from umqtt.simple import MQTTClient

Extra marksThe sharpest justification for MQTT in an IoT design: a device cannot be reached by HTTP. It sits behind NAT with no public address, so an HTTP-only node must poll — waking, connecting and asking "anything for me?" on a timer, which wastes power and adds latency. MQTT's persistent connection lets the broker push a command the instant it arrives. That is why the syllabus pairs REST and MQTT: REST for the device reporting upward, MQTT when the cloud must also talk back.

33 · Interrupts

33.1Polling vs interruptsnamed in syllabus★ high yield

InterruptA hardware signal that suspends the normal flow of the program so that a special function — the Interrupt Service Routine (ISR) — runs immediately, after which execution resumes where it left off. It lets a microcontroller respond to an event without continuously checking for it.
PollingInterrupt
HowThe loop repeatedly reads the pinThe hardware calls you when the pin changes
LatencyUp to one full loop iteration — worse with any delay()Microseconds, and bounded
CPU costWasted cycles checking nothingZero until the event happens
Missed eventsPossible — a short pulse between two checks is lostCaught
PowerCannot sleep — must stay awake to pollCan sleep and be woken by the pin
ComplexitySimpleShared-variable hazards; needs care

Trigger types: rising edge (LOW→HIGH) · falling edge (HIGH→LOW) · both/change · level (while held). Sources are external (a pin) or internal (a timer, the ADC, the UART).

# --- MicroPython on the ESP8266 ---
from machine import Pin
import micropython
micropython.alloc_emergency_exception_buf(100)   # so ISR errors are reportable

count = 0
def handler(pin):          # the ISR — keep it TINY
    global count
    count += 1              # set a flag / bump a counter, nothing more

button = Pin(14, Pin.IN, Pin.PULL_UP)
button.irq(trigger=Pin.IRQ_FALLING, handler=handler)

# --- Arduino C equivalent ---
// volatile: the compiler must not cache a variable an ISR can change
volatile int count = 0;
void isr() { count++; }
attachInterrupt(digitalPinToInterrupt(2), isr, FALLING);
// Uno: only pins 2 and 3 support external interrupts

The rules for writing an ISR:

  1. Keep it as short as possible — set a flag or increment a counter; do the real work in the main loop.
  2. No delay(), no Serial.print, no network calls inside an ISR.
  3. No memory allocation in a MicroPython ISR — no new strings, lists or objects.
  4. Shared variables must be volatile in C, and read atomically if larger than one machine word.
  5. Debounce mechanical switches — one press produces many electrical edges, so ignore edges within ~50 ms of the last one, or filter in hardware with an RC network.
Exam trapOn the Arduino Uno only pins 2 and 3 can raise external interrupts — a question that attaches one to pin 7 is testing exactly this. On the ESP8266 every GPIO except GPIO16 supports interrupts. And the reason volatile exists is examinable in itself: without it the optimiser may keep the variable in a register and the main loop will never see the ISR's change.

Exam trap — final checklist
  1. The ultrasonic distance is halved. The pulse travels there and back.
  2. The ESP8266 has one analog pin. Any design needing two analog sensors needs an external ADC.
  3. The ESP is 3.3 V and not 5 V tolerant; the Uno is 5 V. Mixing them needs a divider or level shifter.
  4. Uno external interrupts exist only on pins 2 and 3, and shared variables must be volatile.
  5. The functional view is technology-independent; the operational view is not. That is the whole reason they are specified separately.
