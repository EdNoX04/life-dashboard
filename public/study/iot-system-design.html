Module 1 · Embedded IoT

Embedded systems

1.1What an embedded system is★ high yield

Embedded systemA combination of hardware and software (often with mechanical parts) designed to perform a specific, dedicated function, usually as part of a larger system.

Six characteristics: single-purpose · autonomous · real-time constraints (hard e.g. airbag vs soft e.g. video buffer) · reactive & always-on · resource-constrained · tightly coupled to hardware.

Six purposes: data collection · communication · signal processing · monitoring · control · application-specific UI.

1.2Microprocessor vs microcontroller★ high yield

MicroprocessorMicrocontroller
ContainsCPU onlyCPU + RAM + ROM + I/O on one chip
NeedsExternal RAM/ROM/peripheralsLargely self-contained

Extra marksHarvard vs von Neumann + added — the decks cover the memory hierarchy but never name these. Harvard = separate instruction and data buses (AVR/ATmega328P — lets it fetch and execute at once); von Neumann = one shared bus (simpler, can bottleneck). Worth a mark under “Memory Architectures”.

IoT levels & views

1.3IoT Levels 1–6 (Bahga & Madisetti)★ high yield

This is what the syllabus means by “IoT level specification”. Each level is defined by how many nodes, and where storage and analysis happen.

LevelNodesStorage / analysisExample
1Single nodeAll local (storage, analysis, app on device)Home temperature monitor
2Single nodeAnalysis local, storage + app in cloudWeather monitoring
3Single nodeStorage + analysis both in cloudWearable health monitor
4Multiple nodesLocal analysis, cloud storage; observer nodesCity traffic sensors
5Many end nodes + 1 coordinatorCoordinator → cloud; cloud analysesSmart agriculture (WSN)
6Multiple independent nodesAll cloud; a central controller commands all nodesSmart city

The jumps: L1→L2 pushes storage to cloud; L2→L3 pushes analysis to cloud; L3→L4 adds multiple nodes; L4→L5 adds a coordinator/gateway; L5→L6 nodes are independent but a central controller oversees them.

Pillars, sensors & actuators

1.5The four pillars of embedded IoT★ high yield

PillarJobExamples
SensingRead the physical worldDHT11, PIR, LDR, ultrasonic
ComputationProcess data on-deviceMCU (AVR, ARM, Xtensa)
CommunicationMove data device↔cloudUART, SPI, I2C, Wi-Fi, MQTT

Remove any pillar and it stops being IoT: no actuation → just monitoring; no communication → a Level-1 standalone device; no sensing → nothing to act on.

1.6Sensors — specs & formulas★ high yield

SensorMeasuresOutputKey spec
DHT11 / DHT22Temp + humidity1-wire digitalDHT11 ±2°C, ≤1 sample / 2 s
PIR (HC-SR501)Motion / presenceDigital HIGH/LOW~7 m, 120°, 4.5–12 V
Ultrasonic (HC-SR04)DistanceEcho pulse width2–400 cm, ±3 mm, 40 kHz
LDRLightAnalog (needs ADC)MΩ dark → few Ω bright
HC-SR04 distance formulaTrigger HIGH for 10 µs → the Echo pin stays HIGH for the round-trip time. Distance = (speed of sound × echo time) / 2, using ≈ 330–343 m/s. The ÷2 is because the pulse travels there and back — forgetting it doubles every reading.

LDR voltage divider: LDR + fixed resistor across 5 V; read the junction with the ADC. As light rises, LDR resistance falls, so the tap voltage swings — that’s how you turn “light” into a number.

Communication models

1.8The four models + REST★ high yield

ModelHow it works
Request–ResponseClient asks, server replies (stateless). REST uses this.
Publish–SubscribePublishers → topics on a broker → subscribers. MQTT uses this.
Push–PullProducers push to a queue, consumers pull; queue buffers rate mismatch.
Exclusive PairPersistent, full-duplex connection. WebSocket uses this.

REST = stateless HTTP APIs on resources (URIs) using GET / POST / PUT / DELETE, payload in JSON. WebSocket = full-duplex persistent link (HTTP Upgrade → 101 Switching Protocols) so the cloud can push to the device instantly.

2.2Sketch structure★ high yield

// Blink — the canonical sketch
void setup() {              // runs once
  pinMode(13, OUTPUT);
}
void loop() {               // runs forever
  digitalWrite(13, HIGH);
  delay(1000);            // ms
  digitalWrite(13, LOW);
  delay(1000);
}

Core API: pinMode, digitalRead/Write, analogRead/Write, delay, and Serial (Serial.begin(9600), Serial.println()). Workflow: write sketch → compile → upload over USB → runs standalone.

Exam trapThe NodeMCU is 3.3 V logic. Feeding a 5 V sensor output straight into a GPIO can damage it — use a divider or level shifter. This is the classic viva question.

MicroPython, Wi-Fi & cloud

2.5MicroPython & flashing+ added

MicroPythonA lean implementation of Python 3 for microcontrollers — you write Python instead of C/C++, and run it interactively over a REPL. Edited in the Thonny or uPyCraft IDE.

Flashing the ESP8266 (once): erase the chip and write the MicroPython firmware with esptool:

esptool.py --port COM3 erase_flash
esptool.py --port COM3 write_flash 0 esp8266.bin

After flashing, the board exposes a Python REPL over serial; boot.py and main.py run automatically at power-on.

2.6Connect to Wi-Fi & POST to the cloud+ added★ high yield

import network, urequests
wlan = network.WLAN(network.STA_IF)
wlan.active(True)
wlan.connect('SSID', 'password')
while not wlan.isconnected(): pass

# REST: POST a reading to the cloud
urequests.post('http://api.example.com/data',
    json={'temp': 28})

REST verbs: GET = read, POST = create/upload, PUT = update, DELETE = remove; payload is JSON. This is the “Interfacing ESP with the Cloud (REST — GET/POST)” syllabus line.

2.7MQTT+ added★ high yield

MQTTMessage Queue Telemetry Transport — a lightweight publish/subscribe protocol over TCP, ideal for constrained IoT devices. Devices publish to a topic on a broker; other devices subscribe to that topic.
QoSGuarantee
0 — at most once"Fire and forget" — may be lost, never duplicated
1 — at least onceGuaranteed delivery, but may arrive twice
2 — exactly onceGuaranteed once — highest overhead

Retained message: the broker keeps the last message on a topic so a new subscriber gets it immediately. MQTT vs REST: MQTT is push-based, persistent, low-overhead (great for many sensors); REST is pull-based request/response. Broker example: Mosquitto; library: umqtt.simple on MicroPython.

Likely questionThe course lab explicitly lists “publish temperature data to an MQTT broker” — expect a question on broker/topic/QoS. The QoS table is the high-value part.

Interrupts

2.8Interrupts+ added★ high yield

InterruptA hardware signal that pauses the main program to run a short ISR (Interrupt Service Routine), then resumes — so the MCU reacts instantly to an event instead of constantly polling for it.
attachInterrupt(
  digitalPinToInterrupt(2),  // pin
  onMotion,                    // ISR
  RISING);                     // trigger edge

Trigger modes: RISING, FALLING, CHANGE, LOW. ISR rules: keep it tiny, no delay() or Serial.print() inside, and mark shared variables volatile. On the Uno only pins 2 and 3 support external interrupts; the ESP8266 allows interrupts on most GPIOs.

Extra marksContrast interrupt vs polling: polling wastes CPU checking a pin in a loop and can miss brief events; an interrupt is event-driven and never misses the edge. That comparison is the most likely exam framing.
